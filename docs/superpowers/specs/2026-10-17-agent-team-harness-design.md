# Обвязка для команды агентов (итерация A1) — дизайн

Дата: 2026-10-17
Статус: на ревью у заказчика

## 1. Контекст и цели

Продукт — Discord-бот, который раздаёт роли по реакциям на сообщение в специальном канале. Способ разработки — команда из четырёх агентов (аналитик, разработчик, тестировщик, девопс) с обвязкой вокруг них.

Главная цель проекта учебная: собрать первую команду агентов и обвязку своими руками, а бот использовать как реальную задачу для этой команды. Поэтому:

- Обвязка проектируется минимальной, но настоящей: гейты принудительные, а не «по договорённости».
- Файлы ролей, hooks и скрипты гейтов пишет заказчик руками по шаблонам. Claude проектирует, объясняет, ревьюит и отлаживает.
- Код бота пишут только агенты. Ни заказчик, ни Claude код бота руками не пишут. Если агенты не справляются, чинится обвязка (промпт, гейт, шаблон), а не код.

Жёсткое ограничение: обвязка должна переноситься на другие инструменты и модели, конкретно на OpenCode с Qwen. Отсюда принцип **«переносимое ядро + тонкие адаптеры»**: промпты в markdown, артефакты в файлах репозитория, логика гейтов в shell-скриптах, а всё специфичное для Claude Code сосредоточено в папке `.claude/`.

### Вне скоупа A1

- Скилл `/team`, автоматизирующий порядок вызова агентов (итерация A2).
- Переезд на OpenCode (итерация B).
- Собственный оркестратор на Agent SDK (итерация C).
- Выбор хостинга для бота. Docker-образ подходит для любого варианта, решение откладывается.
- Любые функции бота за пределами того, что напишет аналитик по задачам 000 и 001.

## 2. Решения, принятые в ходе обсуждения

| Вопрос | Решение | Почему |
|---|---|---|
| Форма обвязки | Сначала команда внутри Claude Code (A), потом свой оркестратор на Agent SDK (C) | Роли и гейты в A стоят ноль кода и целиком переезжают в C. После A будут конкретные места, где LLM-оркестрация ломалась, это ТЗ на C |
| Workflow-скрипт Claude Code | Отклонён | Есть только в Claude Code, при переезде выбрасывается целиком |
| Порядок вызова агентов | Ручная эстафета сейчас, скилл потом | Заказчик хочет прожить каждый шаг руками, прежде чем автоматизировать |
| Цепочка «агент вызывает следующего» | Отклонена | Процесс был бы размазан по четырём промптам, его нельзя прочитать и изменить в одном месте. Вложенность субагентов в Claude Code возможна, но отключается явно |
| Хостинг на Vercel | Отклонён | Реакции на сообщения приходят только через gateway, нужен процесс 24/7, serverless не подходит |
| Паузы в процессе | После каждого агента (режим `step`), позже переключаемый `auto` | Учебная цель. В ручной эстафете пауза после каждого шага получается сама собой |
| Правила проекта | Один AGENTS.md | Его читают и Claude Code (напрямую с версии 2.1.277, у заказчика 2.1.301), и OpenCode. CLAUDE.md из одной строки `@AGENTS.md` на случай сессий, где прямое чтение недоступно |

## 3. Проверенные факты о платформах

Проверено по документации 2026-10-17.

Claude Code:

- Субагент описывается файлом `.claude/agents/<name>.md`: YAML frontmatter + системный промпт в теле. Поля: `name`, `description`, `tools`, `disallowedTools`, `model`, `maxTurns`, `hooks`, `permissionMode` и другие.
- У субагентов отключён `AskUserQuestion`. Вопросы заказчику агент может только вернуть в своём отчёте.
- Субагенты могут вызывать других субагентов (глубина 3 по умолчанию). Отключается `disallowedTools: Agent`.
- Завершённого субагента можно продолжить через `SendMessage`, контекст сохраняется.
- Hook получает на stdin JSON. Внутри субагента там есть `agent_type` и `agent_id`. Для `Stop`/`SubagentStop` есть `last_assistant_message` и `stop_hook_active`.
- `SubagentStop` поддерживает matcher по имени агента. Код выхода 2 не даёт агенту завершиться, stderr передаётся ему как обратная связь.
- `PreToolUse` поддерживает matcher по имени инструмента. Блокировка — JSON `hookSpecificOutput.permissionDecision: "deny"` с `permissionDecisionReason`.
- В hooks доступна переменная окружения `CLAUDE_PROJECT_DIR`.
- CLAUDE.md поддерживает импорт `@path/to/file`.

OpenCode:

- Агенты в `.opencode/agents/<name>.md`, тот же формат frontmatter + промпт. Ключевые поля: `description`, `mode`, `model`, `permission`.
- Читает `.claude/skills/<name>/SKILL.md` напрямую.
- Читает AGENTS.md как правила проекта, CLAUDE.md только как fallback.
- Hooks реализуются TS-плагинами в `.opencode/plugins/`, события `tool.execute.before`, `tool.execute.after`, `session.idle` и другие.
- Есть `@opencode-ai/sdk`; сервер принимает поле `agent` при отправке промпта в сессию.

## 5. Роли

Каждая роль — файл `.claude/agents/<role>.md`. Frontmatter задаёт инструменты и ограничения, тело — системный промпт. Все четыре роли имеют `disallowedTools: Agent` и `model: inherit`. Значения `maxTurns` стартовые, корректируются после задачи 000.

| Роль | Вход | Выход | `tools` | `maxTurns` |
|---|---|---|---|---|
| analyst | описание задачи от заказчика; на повторных вызовах — ответы на открытые вопросы | `docs/specs/NNN-<slug>.md` по шаблону | Read, Glob, Grep, Write, WebFetch, WebSearch | 40 |
| developer | путь к утверждённой спеке; на повторных раундах — путь к отчёту тестировщика | код в `src/`, unit-тесты в `tests/`, зелёные `npm run lint` и `npm test` | Read, Glob, Grep, Edit, Write, Bash | 80 |
| tester | путь к спеке | `docs/reports/NNN-test.md` с вердиктом, свои тесты в `tests/` | Read, Glob, Grep, Edit, Write, Bash | 60 |
| devops | путь к отчёту тестировщика с `PASS` | Dockerfile, compose.yaml, .dockerignore, .env.example, `.github/workflows/ci.yml`, `docs/reports/NNN-deploy.md` | Read, Glob, Grep, Edit, Write, Bash | 60 |

Обязательное содержание системного промпта каждой роли:

- **analyst.** Выясняет цель, сценарии, границы. Пишет критерии приёмки так, чтобы каждый проверялся тестом или ручным шагом. Все неясности выносит в «Открытые вопросы», ничего не додумывает. Не пишет код и не предлагает архитектуру. Отчёт заканчивает списком открытых вопросов или фразой «Открытых вопросов нет».
- **developer.** Работает только от утверждённой спеки. TDD: тест, минимальная реализация, рефакторинг. Логика «эмодзи → роль» без зависимостей от discord.js. Не трогает `docs/specs/` и `docs/reports/`. При работе по отчёту тестировщика закрывает каждый дефект по номеру. Отчёт: что сделано, какие файлы, как запустить тесты.
- **tester.** Проверяет каждый AC-N из спеки и записывает результат с доказательством. Пишет дополнительные тесты на граничные случаи, которые разработчик мог пропустить. Код в `src/` не правит, только документирует дефекты с шагами воспроизведения. Вердикт `PASS`, только если все критерии прошли и дефектов нет.
- **devops.** Делает проект собираемым и запускаемым где угодно: Docker multi-stage, compose с `env_file`, CI. Проверяет `docker build` сам, до отчёта. Не трогает `src/` и `tests/`. Отчёт включает точные команды запуска.

Все роли: не делают git-коммитов, не задают вопросов в теле работы (вопросы только в отчёте), завершают работу коротким отчётом по форме из шаблона передачи.

## 6. Артефакты

Нумерация задач: `NNN-<slug>`, например `001-reaction-roles`. Все артефакты задачи несут этот префикс.

### 6.1 Спека `docs/specs/NNN-<slug>.md`

```
---
task: 001-reaction-roles
status: draft
---
# Название

## Цель
## Пользовательские сценарии
## Критерии приёмки
- AC-1: ...
- AC-2: ...
## Вне скоупа
## Технические ограничения
## Открытые вопросы
```

`status` принимает `draft` или `approved`. Ставит `approved` только заказчик, руками. Спека считается утверждённой, если `status: approved` **и** секция «Открытые вопросы» пуста. Нумерация AC-N обязательна: по ней отчитывается тестировщик и её проверяют гейты.

### 6.2 Отчёт тестировщика `docs/reports/NNN-<slug>-test.md`

```
---
task: 001-reaction-roles
round: 1
verdict: PASS
---
## Проверка критериев
| AC | Результат | Доказательство |
|---|---|---|
| AC-1 | pass | tests/mapping.test.ts: "assigns role for mapped emoji" |
## Дефекты
- D-1: ... шаги воспроизведения ...
## Добавленные тесты
```

`verdict` — `PASS` или `FAIL`. На задачу один файл отчёта: каждый новый раунд перезаписывает его, а `round` растёт на единицу. История раундов сохраняется в git, потому что заказчик коммитит после каждого шага. Каждый AC-N из спеки должен присутствовать в таблице. Результат: `pass`, `fail` или `manual` (проверено руками, с описанием шагов).

### 6.3 Отчёт девопса `docs/reports/NNN-<slug>-deploy.md`

```
---
task: 001-reaction-roles
status: ok
---
## Сборка
## Локальный запуск
## Переменные окружения
## CI
## Отложено
```

`status` — `ok` или `failed`. В «Отложено» фиксируется то, что сознательно не сделано (например, выбор хостинга).

### 6.4 Состояние задачи

Отдельного трекера нет, состояние выводится из файлов:

| Что лежит в репо | Состояние |
|---|---|
| спеки нет | не начата |
| спека `draft` или с открытыми вопросами | анализ |
| спека утверждена, отчёта тестов нет | разработка, раунд 1 |
| последний отчёт тестов `FAIL` | разработка, раунд N+1 |
| последний отчёт тестов `PASS`, отчёта деплоя нет | девопс |
| отчёт деплоя `ok` | готово |

Эта таблица — будущая state machine итерации C.

## 7. Шаблоны передачи `team/handoffs/<role>.md`

Текст, с которым главная сессия вызывает агента. Плейсхолдеры: `{{task}}`, `{{spec}}`, `{{report}}`, `{{answers}}`. Главная сессия подставляет значения и передаёт результат как промпт субагенту. В A2 эти же файлы читает скилл.

Обязательное содержание:

- **analyst.md.** Описание задачи от заказчика. Путь, куда писать спеку, и путь к шаблону. При повторном вызове — блок `{{answers}}` с ответами заказчика и требование обновить спеку, убрав закрытые вопросы. Формат отчёта: путь к спеке, список открытых вопросов.
- **developer.md.** Путь `{{spec}}`. Напоминание о TDD и о границах записи. При повторном раунде — путь `{{report}}` и требование закрыть каждый D-N. Формат отчёта: список файлов, команда тестов, что не удалось (если есть).
- **tester.md.** Пути `{{spec}}` и к шаблону отчёта, номер раунда. Запрет на правку `src/`. Формат отчёта: путь к отчёту и вердикт.
- **devops.md.** Путь `{{report}}` тестировщика. Требование проверить `docker build` до написания отчёта. Формат отчёта: путь к отчёту деплоя и команды запуска.

Каждый шаблон заканчивается одинаковой инструкцией: «Если гейт вернул тебя с ошибкой, исправь причину. Если после трёх попыток не получается, остановись и опиши проблему в отчёте».

## 8. Протокол ручной эстафеты

Заказчик ведёт процесс из главной сессии Claude Code обычными фразами. Главная сессия берёт шаблон передачи, подставляет пути и вызывает агента.

1. «Запусти analyst: <описание задачи>». Аналитик возвращает черновик спеки и открытые вопросы.
2. Заказчик отвечает в чате. Главная сессия продолжает того же аналитика через `SendMessage` с ответами. Повтор, пока вопросов не останется. Заказчик читает спеку и ставит `status: approved`.
3. «Запусти developer на NNN». Разработчик реализует спеку. На завершении срабатывает гейт разработчика.
4. «Запусти tester на NNN». Тестировщик пишет отчёт. На завершении срабатывает гейт тестировщика.
5. При `FAIL`: «Запусти developer с отчётом NNN-<slug>-test.md». После правок снова шаг 4 с `round: N+1`. Лимит три раунда; после третьего `FAIL` разбор с заказчиком. В ручном режиме лимит соблюдает заказчик.
6. При `PASS`: «Запусти devops на NNN». На завершении срабатывает гейт девопса.
7. После каждого шага заказчик смотрит результат и делает коммит сам.

Полная версия протокола с примерами фраз — в `team/README.md`.

## 9. Гейты и hooks

### 9.1 Проводка в `.claude/settings.json`

```json
{
  "permissions": {
    "allow": [
      "Bash(npm test:*)",
      "Bash(npm run lint:*)",
      "Bash(npm run build:*)",
      "Bash(npx vitest:*)",
      "Bash(docker build:*)"
    ]
  },
  "hooks": {
    "SubagentStop": [
      { "matcher": "analyst",   "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/team/gates/analyst.sh" }] },
      { "matcher": "developer", "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/team/gates/developer.sh" }] },
      { "matcher": "tester",    "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/team/gates/tester.sh" }] },
      { "matcher": "devops",    "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/team/gates/devops.sh" }] }
    ],
    "PreToolUse": [
      { "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/team/gates/path-policy.sh" }] },
      { "matcher": "Agent",      "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/team/gates/start-policy.sh" }] }
    ]
  }
}
```

Список `permissions.allow` убирает запросы разрешений на команды, которые гейты и агенты выполняют постоянно. Расширяется по мере появления шума.

### 9.2 Общий контракт скриптов

- Вход: JSON на stdin. Используются только поля `hook_event_name`, `agent_type`, `agent_id`, `cwd`, `tool_input.file_path`, `tool_input.subagent_type`, `tool_input.prompt`. Разбор через `jq`.
- Выход для `SubagentStop`: код 0 — пропустить; код 2 + причина в stderr — вернуть агента на доработку.
- Выход для `PreToolUse`: код 0 без вывода — разрешить; код 0 + JSON на stdout вида `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}` — запретить.
- Каждое срабатывание пишется строкой в `.team/gate.log`: время, имя гейта, `agent_type`, результат (`pass`, `block`, `limit`, `deny`), причина. По этому логу проверяется критерий «каждый гейт сработал хотя бы раз».
- Общие функции (чтение stdin, лог, счётчик попыток) в `team/gates/common.sh`, остальные скрипты его подключают.
- Специфичного для Claude Code в скриптах нет. Плагин OpenCode подаёт им такой же JSON.

### 9.3 Счётчик попыток

Гейты `SubagentStop` ведут счётчик по `agent_id` в `.team/attempts/<agent_type>-<agent_id>`. На каждом блоке счётчик растёт. При третьем провале гейт возвращает код 0 (выпускает агента), пишет в лог результат `limit` и причину. Это защита от бесконечного цикла «агент не может починить — гейт не отпускает». Страховка второго уровня — `maxTurns` в frontmatter роли.

### 9.4 Гейты завершения

| Скрипт | Как находит задачу | Проверки | Причина в stderr при блоке |
|---|---|---|---|
| `analyst.sh` | свежайший по mtime файл в `docs/specs/` | файл существует; frontmatter с `task` и `status`; все шесть заголовков `## ` из шаблона на месте; хотя бы одна строка `- AC-N:` | «нет секции X» или «нет ни одного критерия приёмки» |
| `developer.sh` | не нужна | `package.json` существует и содержит скрипты `test` и `lint`; `npm run lint` и `npm test` завершаются кодом 0 | хвост вывода упавшей команды (последние 40 строк) |
| `tester.sh` | свежайший по mtime файл `docs/reports/*-test.md`, из его frontmatter `task` → `docs/specs/<task>.md` | отчёт существует; `verdict` равен `PASS` или `FAIL`; каждый `AC-N` из спеки встречается в таблице отчёта; `npm test` завершается кодом 0 | «в отчёте нет AC-3, AC-5» или вывод тестов |
| `devops.sh` | свежайший по mtime файл `docs/reports/*-deploy.md` | отчёт существует со `status`; `Dockerfile` существует; `docker build -q .` завершается кодом 0; `.github/workflows/ci.yml` существует и содержит строку `jobs:` | вывод `docker build` или «нет файла X» |

Гейт `developer.sh` при отсутствии `package.json` блокирует с понятным сообщением. Это важно для задачи 000, где разработчик создаёт проект с нуля: гейт заставляет сразу завести скрипты `test` и `lint`.

### 9.5 Политика путей `path-policy.sh`

Срабатывает перед каждым `Edit` и `Write`. Если в stdin нет `agent_type` (главная сессия) — разрешить. Если `agent_type` не из четырёх ролей — разрешить и записать в лог. Иначе путь (относительно `cwd`) сверяется с таблицей:

| Роль | Разрешено писать |
|---|---|
| analyst | `docs/specs/` |
| developer | всё, кроме `docs/specs/` и `docs/reports/` |
| tester | `tests/`, `docs/reports/` |
| devops | `Dockerfile`, `.dockerignore`, `compose.yaml`, `.env.example`, `.github/`, `docs/reports/` |

Запрет возвращается как `permissionDecision: "deny"` с причиной вида «роль tester не может писать в src/handlers.ts; разрешено: tests/, docs/reports/».

Известное слабое место: политика покрывает только `Edit` и `Write`. Запись через Bash (`echo > file`) не перехватывается. Для A1 это принимается; разбор Bash-команд вне скоупа.

### 9.6 Политика старта `start-policy.sh`

Срабатывает перед вызовом инструмента `Agent` в главной сессии. Из `tool_input.subagent_type` берётся роль, из `tool_input.prompt` регулярным выражением — путь к артефакту: для developer и tester первый путь вида `docs/specs/[^\s]+\.md`, для devops первый путь вида `docs/reports/[^\s]+-test\.md`. Промпт разработчика на повторном раунде содержит и спеку, и отчёт, поэтому тип пути привязан к роли. Проверки:

| Роль | Условие старта |
|---|---|
| analyst | без условий |
| developer | спека найдена в промпте, `status: approved`, секция «Открытые вопросы» пуста |
| tester | спека найдена, `status: approved` |
| devops | отчёт тестировщика найден, `verdict: PASS` |

Если роль не из четырёх — разрешить. Если артефакт в промпте не найден — запретить с причиной «в промпте нет пути к спеке». Так разработчик физически не стартует на неутверждённой спеке, а девопс — без зелёного вердикта.

### 9.7 Тесты гейтов `team/gates/test.sh`

Для каждого скрипта минимум один положительный и один отрицательный случай. Тест создаёт временную директорию с фикстурами из `team/gates/fixtures/` (правильная спека, спека без критериев, отчёт без AC-2, пустой проект без `package.json`), подаёт на stdin подготовленный JSON и проверяет код выхода и ключевые слова в stderr или в JSON на stdout. Проверки, требующие `npm test` и `docker build`, в тестах гейтов заменяются подстановкой фиктивных команд через переменную окружения `GATE_DRY_RUN=1`, при которой `common.sh` подменяет вызовы на заранее заданные коды выхода. Запуск: `bash team/gates/test.sh`, выход 0 означает, что все случаи прошли.
