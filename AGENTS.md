# AGENTS.md

Инструкция для ИИ-агентов и разработчиков. Прочитай целиком перед правками.

## Что это

**Бармен** — Discord-бот на [Hermes Agent](https://github.com/NousResearch/hermes-agent) (Nous Research), профиль Hermes `barmen`, плагин `barman/`.

Что умеет: роли по реакциям в канале раздачи ролей. Участник ставит любую реакцию под привязанным сообщением → получает роль; снимает → роль снята. Одно сообщение = одна роль.

Управление — только для тех, у кого есть право «Управлять ролями» (остальные команды не видят), только в канале ролей, ответы бота видит только вызвавший (ephemeral):

- ПКМ по сообщению → Приложения → «Привязать роль» / «Отвязать роль». В меню только роли, которые модератор может привязать, а бот — выдать; после привязки бот ставит ✅ под сообщением. Отвязка не снимает уже выданные роли.
- `/роли` — список привязок с пометкой ⚠️ и подсказкой, если роль удалена, выше бота, стала модераторской или сообщение удалено
- `/синк` — выдать роли тем, кто уже стоит в реакциях; заодно убирает привязки удалённых сообщений

Ещё бармен раз в день в **21:00 по Москве** постит в заданный канал выжимку DTF (`barman/digest.py`): 10 самых популярных постов за день по лайкам + комментариям — сначала редакционные новости, затем добор популярными постами; к каждому пересказ ИИ (OpenRouter, по умолчанию `anthropic/claude-haiku-4.5`; при сбое — описание от DTF) и упоминание одного участника. Первый выпуск — сразу при первом запуске; время последнего выпуска хранится в `/root/barmen-hermes/barman/digest.json`, перезапуски не дублируют пост, пропущенные 21:00 догоняются при старте.

Язык всего, что видят люди, — **русский**.

## Структура

```
barman/
  __init__.py        register(ctx): слушатели реакций и команды Discord (discord.py внутри Hermes)
  reaction_roles.py  чистая логика: привязки, проверки, синхронизация команд — без импорта discord
  digest.py          чистая логика ежедневной выжимки DTF: отбор, пересказ, расписание — без discord и сети
  comments.py        чистая логика редких реплик на сообщения завсегдатаев — без discord и сети
  conversation.py    ограниченный SDK-эпизод владельца и собеседника для пилота
  screenshots.py     локальный OCR, маскирование текста/лиц и метаданные приватности
  link_pilot.py      выключенный по умолчанию недельный пилот одной ссылки
  link_research.py   image-only IDENTIFY → RESOLVE → native SEARCH → публичный fetch → CHECK
  plugin.yaml        манифест плагина (kind: standalone)
tests/               pytest, без сети и без discord.py
deploy/update.sh     выкатка на сервер (BARMAN_TARGET=prod — бар, test — тестовый бот)
deploy/render_soul.py сборка SOUL.md: заглушки эмодзи → <:имя:ID>
deploy/Dockerfile.ocr необязательный производный образ с локальным OCR и OpenCV
persona/            личности бармена: SOUL.sibiya.md, SOUL.fidel.md, SOUL.angmar.md, SOUL.drakonia.md
```

## Разработка

```bash
~/.local/bin/uv venv -p 3.12 .venv && ~/.local/bin/uv pip install -p .venv/bin/python -e ".[dev]"
.venv/bin/pytest -q            # все тесты зелёные перед коммитом
```

- **TDD:** сначала падающий тест, потом код. Логику выносить в `reaction_roles.py` и тестировать там.
- Импорты внутри плагина — **только относительные** (`from .reaction_roles import …`): Hermes грузит папку как `hermes_plugins.barman`.
- `discord` импортируется только внутри фабрики (его даёт Hermes). Модуль под `from __future__ import annotations`, поэтому тип параметра контекстного меню задаётся объектом (`callback.__annotations__[...] = discord.Message`).
- В Discord у бота только команды бармена (`/роли`, `/синк`, «Привязать/Отвязать роль»). Hermes свои команды не регистрирует (`DISCORD_COMMAND_SYNC_POLICY=off`), а бармен при старте (`sync_app_commands`) перезаписывает список своими, если там есть чужие, иначе досылает недостающие по одной. Массовый `tree.sync()` не использовать — он зальёт ~70 команд Hermes.
- ИИ бармена (Hermes) разговаривает только с теми, кто в `DISCORD_ALLOWED_USERS` (секрет `BARMAN_AI_USERS`, ID через запятую; нет секрета — `0`, ни с кем), только в `DISCORD_ALLOWED_CHANNELS` (секрет `BARMAN_AI_CHANNELS`) и только по упоминанию. Без списка пользователей Hermes пускает всех из `DISCORD_ALLOWED_CHANNELS` — поэтому `0`, а не пусто.
- Служебные команды Hermes (`/model`, `/update`, `/restart`, навыки…) закрыты для всех, даже для пущенных к разговору: в `config.yaml` `platforms.discord.extra.allow_admin_from` и `group_allow_admin_from` = `0` (админов нет) — остаются только `/help` и `/whoami`. Личка выключена: `dm_policy: disabled`. Выкатка ставит эти замки через `hermes config set`, проверяет их и только потом открывает доступ; не встали — стоп.
- Отвечает прямо в канале, без веток (`DISCORD_AUTO_THREAD=false`), и в ветках тоже только по упоминанию (`DISCORD_THREAD_REQUIRE_MENTION=true`, иначе в ветке Hermes отвечает на всё подряд), реплаем на сообщение того, кто обратился — пингуется только он (`DISCORD_REPLY_TO_MODE=first`, пинги @user/@role/@everyone в тексте ответа выключены). Домашнего канала нет (`DISCORD_HOME_CHANNEL=0`): служебные сообщения Hermes никуда не уходят, подсказки «/sethome» нет. Дописали, пока он думает, — отвечает отдельно, без служебных плашек (`display.busy_input_mode: queue`, `HERMES_GATEWAY_BUSY_ACK_ENABLED=false`).
- Реплики без обращения (`barman/comments.py`, не Hermes): на сообщения людей из секрета `BARMAN_COMMENT_USERS` в канале `BARMAN_AI_CHANNELS` бармен изредка отвечает одной фразой — шанс `BARMAN_COMMENT_CHANCE` (0.1), не чаще раза в `BARMAN_COMMENT_COOLDOWN_MIN` (60) минут, реплаем без пинга, голосом из `SOUL.md`; модель — `BARMAN_AI_MODEL`. Не реагирует на обращения к себе (их отвечает Hermes), ссылки, команды и короткое; модель может промолчать (SKIP). Нет секрета — выключено. Случайные реплики без обращения у Ангмара сейчас выключены и в prod, и на test; это отдельная настройка от пилота ссылок.

- Hermes запоминает системный промт (личность) и настройки в момент создания сессии и держит одну открытую сессию на канал. Архив (`hermes sessions archive`) её не закрывает, а `prune` открытые не трогает. Поэтому выкатка перед перезапуском находит открытые Discord-сессии, в чьём промте нет текущей SOUL.md (`deploy/stale_sessions.py`, базу только читает), и удаляет их `hermes sessions delete <id> --yes`: новая личность вступает в силу со следующего сообщения. Сессии с актуальной личностью остаются вместе с историей.
- Инструментов у ИИ в Discord нет (`platform_toolsets.discord: []`) — не включать: с инструментом ИИ дотянется до `.env` с ключами.
- Личность — `persona/SOUL.<имя>.md` (`sibiya`, `fidel`, `angmar`, `drakonia` — язвительная хозяйка стойки, перенесена из проекта компаньонов без флирта и отсылок к «Гарри Поттеру»), выбирается секретом `BARMAN_SOUL`. Переключить: `gh secret set BARMAN_SOUL --body fidel` и Actions → deploy → Run workflow. Новая личность — новый файл в `persona/` с теми же неизменными правилами (их проверяет тест) и эмодзи только заглушками. Эмодзи сервера в личности — заглушки `{{emoji:peka}}`; выкатка подставляет `<:peka:ID>` из секрета `BARMAN_EMOJI` (`peka=ID,neponi=ID,…`), ID в репо не кладём (`deploy/render_soul.py`).
- `deploy/update.sh` работает от root, но пишет в папку, которую контролирует процесс бота (uid 10000). Правило: никаких записей «по месту» — только новый файл через `mktemp` в той же папке, владелец `10000:10000` до `mv -f` поверх; если `.env`, `SOUL.md`, `config.yaml`, `plugins` или `plugins/barman` оказались символической ссылкой — выкатка останавливается до любых действий; код плагина копируется `rsync --no-links`. Проверяется `tests/test_update_sh.py`. Остаётся узкая гонка (ссылку подложат между проверкой и `rsync --delete`) — полностью закрывается только записью от uid 10000; и ключ выкатки пока даёт полный root (ограничить одной командой, как у компаньона, — отдельная задача).
- Секреты только в `.env` профиля на сервере. В репозитории (он публичный) — никаких токенов, ID и ключей.

## Известные ограничения (приняты для маленького сервера)

### Актуальное видение и политика чата (2026-11-07)

- Основа — надёжная выдача и снятие ролей по реакциям. Разговор — максимум два коротких предложения. Возможные будущие функции: патчноуты популярных игр и билды ARPG; это направления, не обязательства.
- Новая политика заменяет прежнее ограничение каналов выше: `DISCORD_ALLOWED_CHANNELS=*`, но входной хук `barman/chat.py` допускает только сервер опорного канала `BARMAN_SCOPE_CHANNEL` (выкатка берёт канал ролей или первый из `BARMAN_AI_CHANNELS`; резерв — прежний `BARMAN_ROLES_CHANNEL`). Нет канала/бота в кеше — отказ. Прежний список пользователей и требование обращения сохраняются; `BARMAN_AI_CHANNELS` также ограничивает редкие реплики без обращения.
- Инструменты Hermes остаются выключены (`platform_toolsets.discord: []`). Секрет `BARMAN_SEARCH_USERS` (на тесте `TEST_BARMAN_SEARCH_USERS`) задаёт полный список Discord ID для изолированного OpenRouter `openrouter:web_search`: Exa, один поиск, максимум три результата. Разрешены Sibiya, Фидель и Ангмар; реальные ID только в секретах. Этот список имеет приоритет над прежним одиночным `BARMAN_SEARCH_OWNER`; если списка нет — используется прежний владелец, нет обоих — поиск закрыт. `BARMAN_SEARCH_USERS=0` закрывает поиск всем. Настоящий `raw_message.author.id` должен входить и в список поиска, и в `DISCORD_ALLOWED_USERS`; имя, роли и текст прав не дают. Личка, чужие серверы, боты и вебхуки не допускаются.
- Поиск универсален: смысл запроса и продолжений определяет модель, без тематических маршрутизаторов, словарей вопросов и белых списков доменов. `dialogue.py` хранит до четырёх последних пар «вопрос/ответ» только этого пользователя в этом канале, на 15 минут, до 128 диалогов. Ключ — SDK guild/channel/author; память читается после проверки прав, пополняется после успешной доставки. Общая история канала, backfill, вложения и тексты найденных страниц не передаются. Известные ключи профиля вырезаются из запросов, памяти, ответов и аудита. Обычный изолированный чат не загружает произвольные URL и не исполняет команды; ограниченный публичный fetch чернового пилота описан отдельно ниже. Ключ API используется только HTTP-заголовком.
- `transform_llm_output` ограничивает разговор двумя предложениями и 500 символами. Потоковая отправка выключена (`streaming.enabled=false`, `display.platforms.discord.streaming=false`), чтобы текст сократился до публикации; установленный Hermes ещё не поддерживает `hold_stream`. Probe сверяет сигнатуру настоящего `PluginContext.register_hook`. В ответе владельцу — не более одной HTTPS-ссылки из цитат провайдера, без локальных адресов. Запросы владельца идут по одному, очередь до трёх, при переполнении — короткий ответ. Склейка входных сообщений Discord отключена, чтобы каждое обращение сохранило собственный проверенный текст.
- Перед расширением каналов выкатка проверяет API хуков, регистрацию политики и пустой toolset (`deploy/check_chat_runtime.py`). Сначала тестовый стенд; перенос в Паб — после проверки. При архитектурном ревью сохранять чистую логику отдельно от Discord и сети, тесты без сети, изоляцию секретов и путь `test` → `main`.
- Качество ответа: модель возвращает внутренний JSON `kind/answer/source_url/quote`. Для `fact` код требует положительный `web_search_requests`, безопасную HTTPS-ссылку из результатов именно текущего запроса и дословную цитату длиной 20–600 символов, которая содержится в заголовке/выдержке этого источника. Ссылка выбирается моделью по смыслу, а не берётся первой. JSON/оборванный ответ/неподтверждённые факты не публикуются как результат поиска. Для беседы и уточнения поиск не обязателен. Модель должна предпочитать первоисточники, различать публикацию и последний комментарий, не выполнять инструкции из страниц. Эти проверки доказывают происхождение цитаты и обращение к поиску, не абсолютную истинность каждого утверждения. «Поешечка = PoE 2» хранится только как знание конфы в персонажах, не как алгоритм поиска.
- После отправки `reply_audit` пишет ID входного/исходного сообщения, ID генерации, фактический счётчик поиска (или null, если провайдер его не вернул), источник без query/fragment, число предложений прозы, длину прозы и всего сообщения, число сообщений личного контекста, длину подтверждающей цитаты, причину отказа и результат доставки. Текст переписки, ключи и тела ответов провайдера в этот журнал не пишутся. Ссылка отдельно от прозы не считается предложением.
- Уточнение дополняет исходную цель запроса, не заменяет её. В информационных ответах полезность важнее запрета пересказов из личности; допустим краткий частичный ответ с обозначением пробела. При `not_found`, неподтверждённом или оборванном результате разрешена ровно одна дополнительная попытка с восстановлением полного вопроса и переформулировкой поиска; каждая попытка имеет прежний бюджет поискового инструмента и 4096 токенов генерации. После каждого поиска с результатами отдельный вызов без инструментов и личности оценивает соответствие исходному вопросу и собирает ответ из выдержек. Если материал отвечает лишь на соседний вопрос, он задаёт полную поисковую формулировку для повторной попытки. Отдельная оценка не добавляет источников или счётчиков: они берутся только из реальной поисковой попытки; ID оценки журналируется отдельно. Повторно проходят те же проверки цитаты, источника и двух предложений. Беседа, корректное уточнение и успешный поиск не повторяются. В аудите `attempts` — метаданные каждой начатой попытки, включая ошибки HTTP/таймаут, без переписки и тел страниц. Повтор получает причину отказа и до трёх выдержек прошлой попытки как недоверенные данные с редактированием секретов; для публикации всё равно нужна цитата из новых результатов. Пустой итог после обеих попыток не превращается в выдуманный факт.
- Пилот `link_pilot.py` остаётся выключенным, PR — draft. Для явной активации нужны приватные `.env` `BARMAN_LINK_PILOT_OWNER`, `BARMAN_LINK_PILOT_START`, `BARMAN_LINK_PILOT_UNTIL` с часовым поясом и окном не более семи суток; перезапуск срок не продлевает. Принимаются только новые человеческие сообщения своего сервера без вебхуков и обращения к самому боту; ретроответов нет.
- `conversation.py` собирает эпизод владельца и текущего собеседника по SDK-идентичностям в одном guild/channel: до четырёх предков reply-цепочки, просмотр не более 24 недавних сообщений, максимум восемь выбранных реплик и два вложения. Добор недавних реплик ограничен 12 часами; проверенный более старый корень reply-цепочки сохраняется без такого добора. Обращение устанавливается SDK-упоминанием владельца или проверенной цепочкой к нему. Неявное продолжение допустимо только без собственного reply, длиной до 300 символов, сразу после SDK-ответа владельца этому собеседнику в пределах пяти минут, без вмешательства другого человека. Текст и имя канала не доказывают идентичность или права; сбой SDK не устанавливает неявное обращение.
- До внешних вызовов локально обезличиваются вопрос, выбранные реплики и подсказки: удаляются известные имена/ники участников, SDK-идентификаторы, известные секреты, контакты, ссылки, код и локальные пути. Список участников и полный канал наружу не передаются; из SOUL используется только публичная строка словаря сокращений. Бюджет контекста 1800 символов делится между репликами. Все сообщения, словарь, изображения и страницы — недоверенные данные, не инструкции. Разрешён только обезличенный вариант.
- Скриншоты загружаются только из SDK-вложений на разрешённых Discord CDN, без редиректов, с ограничением чтения; spoiler исключён. `screenshots.py` по умолчанию использует локальный detector-only RapidOCR `3.10.0` с `onnxruntime`: без распознавания строк, классификатора и автоматического fallback. Упакованная модель `PP-OCRv6_det_small.onnx` (около 10 МБ) проверяется по SHA-256 `090f04abcd9d9a7498bc4ebf677e4cb9bdce1fe4197ddb7e529f1ef44e1ff94f` до загрузки; отсутствие или несовпадение модели означает отказ. Runtime-загрузок моделей нет, телеметрия ONNX Runtime отключена. Детекция выполняется локально в двух масштабах; все найденные текстовые области закрываются с отступом, без белого списка надписей. Затем очищенный результат повторно проверяется в двух масштабах, остаточные области маскируются. Границы: вход до 8 МиБ и 8 Мп, рабочий кадр детекции до 16 Мп, выход до 1280 пикселей по стороне и data URL до 2 МиБ. SVG, анимация, повреждённые форматы и decompression bomb отклоняются, EXIF удаляется. Недоступный или ошибочный детектор приводит к отказу, исходное изображение наружу не передаётся. Tesseract `rus+eng` доступен только как явно выбранный legacy backend; его процесс ограничен 20 секундами и размером вывода, при таймауте/отмене выполняются kill, drain и reap.
- Найденные лица закрываются локальным Haar-фильтром OpenCV (`cv2.data.haarcascades/haarcascade_frontalface_default.xml`). Метаданные `faces`, `faces_masked`, `face_detection_available` и `limitations` описывают найденные лица и доступность фильтра, а не отсутствие пропущенных. Модуль явно сообщает о недоступном детекторе; интеграция пилота при этом отклоняет изображение. В API передаётся только очищенный `image_url`; OCR `text` помечен `text_local_only=True`, не передаётся наружу и не журналируется даже после scrub. Это best effort: OCR/детектор могут пропустить подписи, лица и другие личные данные, гарантии полной анонимности нет. Реальные скриншоты переписки не коммитить, тестовые изображения — синтетические.
- Архитектура `link_research.py`: при наличии снимков независимый image-only `IDENTIFY → RESOLVE → native SEARCH → bounded public fetch → CHECK`; без снимков `IDENTIFY` пропускается. `IDENTIFY` получает только очищенные изображения, без вопроса, эпизода, словаря и имени канала; возвращает базовый `product`, видимые `interface_facts`, визуальные `evidence`, `confidence` и неподтверждённые `variant/addon=UNKNOWN`. Идентификация продукта отделена от намерения вопроса, редакцию/расширение нельзя угадывать по стилю интерфейса. При снимках `channel_hint` удаляется и из последующего payload. `RESOLVE` восстанавливает исходный публичный вопрос и отношение ко времени, отсекает личные сведения владельца, беседу и неясный предмет по `scope`; при уверенной идентификации нормализованный `entity` обязан совпадать с `identity.product`. `SEARCH` использует `openrouter:web_search` с Exa: верхнеуровневый `max_tool_calls=1` и `max_uses=1` в параметрах инструмента, до пяти результатов за попытку. До двух поисковых попыток, до трёх новых URL за попытку и шести суммарно, общий таймаут исследования 180 секунд. `CHECK` работает отдельно без инструментов, получает исходный обезличенный вопрос, эпизод, независимую identity, очищенные снимки и тексты источников; скрытые подписи не выдумываются. При повторе `check_feedback.reason` описывает недоказанные условия, а `retry_query` остаётся недоверенной поисковой подсказкой: они не заменяют исходный вопрос/`query`, не меняют продукт, ограничения и фокус на нативной реализации продукта. Исходная цель и независимая identity сохраняются во всех попытках.
- Публичный fetch отделён от API-клиента: без Authorization, cookies и environment proxy; безопасные HTTPS-адреса проверяются на публичность IP в URL и DNS, каждый переход проверяется заново, автоматические редиректы выключены. На документ — до четырёх HTTP-шагов, 15 секунд, 350000 байт, только HTML/plain text и до 18000 символов извлечённого текста. При недоступной странице возможна проверка заголовка/выдержки текущего индекса с отметкой `search_index`, а не выдача её за прочитанную страницу. `CHECK` независимо определяет канонический базовый `source_product` по самому источнику и подтверждает предмет, намерение, время и наличие ответа; при `identity.confidence=high` код дополнительно требует совпадения нормализованных `source_product` и `identity.product`, иначе кандидат отклоняется. Каждое существенное условие вопроса должно прямо подтверждаться источником: отсутствие упоминания не доказывает отрицание, общий тематический матч не заменяет ответ; код требует URL из текущих кандидатов и дословную цитату длиной 20–600 нормализованных символов в тексте выбранного источника. Для `upcoming` нужна ровно одна распознанная дата не раньше текущей московской даты; маркеры публикации/редактирования/поднятия поста приводят к отказу. Это проверки происхождения и релевантности, не гарантия истинности.
- После 20 секунд ожидания, после обработки вложений, перед КАЖДЫМ вызовом модели (`IDENTIFY`, `RESOLVE`, каждым `SEARCH` и `CHECK`) и перед отправкой `still_needed` перепроверяет срок, бюджет, неизменность вопроса и всех использованных реплик/ID вложений, отсутствие ответа владельца или уже отправленного ботом ответа. Ошибка проверки отменяет дальнейшие вызовы. Если после вопроса набралось 30 сообщений, отсутствие ответа нельзя доказать — отказ. Публикуется только одна подтверждённая HTTPS-ссылка без пинга; при ошибке, устаревании и неподтверждении — тишина. Лимиты: 25 проверок и 10 ссылок в сутки, одна ссылка участнику в час, один worker, до трёх принятых задач; переполнение журналируется. `barman/link-pilot.json` хранит дедупликацию, решения и метаданные без текстов; аудит не содержит переписку, OCR и тела страниц.
- `BARMAN_VISION_MODEL` — необязательная отдельная модель всего исследовательского pipeline эпизода с изображениями: `IDENTIFY`, `RESOLVE`, native `SEARCH` и `CHECK`; сам `SEARCH` получает текстовые наблюдения identity и обезличенный контекст без изображения. Без настройки используется `BARMAN_SEARCH_MODEL`. Для vision-проверок выбран Sonnet из-за ошибок Haiku в определении продукта по изображению. Запросы без изображений, включая их native `SEARCH`, сохраняют Haiku/`BARMAN_SEARCH_MODEL`; глобальная текстовая модель не меняется. Vision-маршрут не отменяет проверок продукта, цитаты, срока и актуальности запроса.
- `deploy/Dockerfile.ocr` — необязательный производный образ: база задаётся `BASE_IMAGE`, устанавливаются совместимый `opencv-python-headless<5`, `rapidocr==3.10.0` и `onnxruntime`; SHA-256 упакованного `PP-OCRv6_det_small.onnx` проверяется при сборке. Tesseract `rus`/`eng` установлен для явно выбираемого legacy backend. Pillow требуется в базовом runtime, зависимости изображения импортируются лениво; итоговый uid/gid — `10000:10000`. Локальная проверка покрытия известной подписи маской выполнена; серверная проверка детектора с `--network none` и проверкой SHA пройдена. Полный набор тестов: 337 passed, 2 optional skipped. Эти проверки не активируют пилот: он остаётся выключенным, PR — draft; выкатка и включение требуют отдельных действий.

- Выжимка DTF берёт неофициальный API `api.dtf.ru/v2.8/timeline?sorting=day` (лента «популярное за день», ~130 постов). Сменится API — выпуск упадёт (3 попытки раз в 10 минут, потом пропуск до завтра), смотреть `agent.log`. Текст DTF и ответ ИИ — чужие данные: из них вырезаются все упоминания, пингуется только `BARMAN_DIGEST_USER`.

- Снятие реакции и `/синк` перечисляют всех, кто поставил реакции на привязанных сообщениях (точечного запроса «стоит ли реакция у X» в API нет). На больших сообщениях это много запросов и риск rate limit.
- Очистка реакций модератором («Remove All Reactions» или один эмодзи): Discord не сообщает, чьи реакции ушли. Бармен проверяет всех, у кого роль сейчас есть (по кешу участников — нужен intent Server Members; кого нет в кеше, того не трогаем), одним снимком реакций, а кандидатов на снятие перепроверяет по одному (`revoke_after_clear`). На роли с сотнями участников это много запросов.
- `/синк` должен уложиться в 15 минут (срок жизни interaction), иначе итог не придёт.
- При сбое Discord во время проверки реакций роль **не** снимается (fail-closed) — лучше лишняя роль, чем отнятая.

## Ветки и мерж

- Любое изменение — в отдельной ветке от свежего `main` (`feat/…`, `fix/…`, `docs/…`, `chore/…`), в `main` только через PR.
- **Напрямую коммитить, пушить или вливать в `main` нельзя никому**, включая владельца (ruleset «main: только через PR…» + защита ветки).
- **Любой PR требует апрува владельца кода** (@Sibiya666, `.github/CODEOWNERS`); новый push в PR сбрасывает апрув. Чужой PR вливается только после апрува владельца.
- **Свои PR владелец вливает сам** в обход апрува (одобрить собственный PR GitHub не даёт): кнопка «Merge without waiting for requirements» или `gh pr merge <N> --admin --squash`. Тесты этим не обойти — `main` требует зелёный `pytest` и от админа.
- **ИИ-агенты PR не вливают** (ни `--admin`, ни `--auto`): создают PR, доводят до зелёных тестов и сообщают владельцу номер PR.

## Две ветки: test и main

- **`test` → тестовый бот** (`barmen-test`, секреты `TEST_*`): каждый push в `test` выкатывает тестового бота. **`main` → бармен «Паба»**.
- Порядок: ветка фичи от свежего **`test`** → PR в `test` (squash) → проверка вживую на тестовом сервере → **PR `test` → `main`**.
- PR `test` → `main` вливается **обычным merge, без squash** (`gh pr merge <N> --admin --merge`): иначе истории разойдутся и следующий PR из `test` снова покажет уже влитое и даст конфликты.
- Срочная правка прямо в `main` (мимо теста) — после мержа сразу влить `main` обратно в `test` (`git switch test && git merge origin/main && git push`), чтобы тест не отставал.

## Как изменение попадает в main

1. Локально: ревью пройдено, все замечания исправлены, `.venv/bin/pytest -q` зелёный.
2. `gh pr create --fill --base test` — PR в `test`; проверили на тестовом боте — `gh pr create --base main --head test` (без автомержа: с обязательным апрувом он всё равно не сработает).
3. GitHub Actions гоняет `pytest` на PR (`.github/workflows/tests.yml`). Красный — чинить в той же ветке.
4. Конфликт с `main`: `git fetch && git merge origin/main`, поправить, `pytest`, push.
5. Владелец вливает PR: фичу в `test` — `--squash`, `test` в `main` — `--merge` (или кнопкой с тем же способом). Ветка фичи на GitHub удаляется сама; `test` — нет: её защищает ruleset «test: не удалять и не перезаписывать» (нельзя удалить и force-push; обычные push и PR — можно).
6. После мержа GitHub сам выкатывает на VPS (`.github/workflows/deploy.yml`: тесты → `deploy/update.sh`). Руками — только `deploy/update.sh <IP>` из свежего `main`.

## Неснимаемые правила

1. Роли с правами модерации/администрирования по реакции не выдаются никогда (`is_privileged`), даже если их привязали.
2. Привязать можно только роль ниже собственной высшей роли (кроме владельца сервера).
3. Команды управления — только с правом «Управлять ролями».

## Где работает и как выкатывать

- Прод: VPS (IP знает владелец, в публичный репо не писать). Отдельный Docker-контейнер **`barmen`** (образ `nousresearch/hermes-agent`, `--memory 768m`, `restart unless-stopped`), данные — `/root/barmen-hermes` → `/opt/data` (владелец uid **10000**). На том же сервере в своём контейнере `hermes` живут другие боты — их не трогать.
- Вход: `ssh -i ~/.ssh/companion_vps root@<IP>`.
- Выкатка: `deploy/update.sh <IP>` — rsync плагина в `/root/barmen-hermes/plugins/barman` и `docker restart barmen`.
- **Тестовый бармен** — отдельный бот (своё приложение Discord и токен), контейнер `barmen-test`, данные `/root/barmen-test-hermes`. Выкатывается из ветки **`test`**: каждый push в неё — тесты и выкатка на тестового бота (`.github/workflows/deploy-test.yml`), как `main` → бар. Вручную — Actions → **deploy-test** → Run workflow. Настройки — те же секреты с префиксом `TEST_` (`TEST_DISCORD_BOT_TOKEN`, `TEST_BARMAN_AI_USERS`, `TEST_BARMAN_AI_CHANNELS`, `TEST_BARMAN_SOUL`, …). Первая выкатка создаёт его сама: `config.yaml` и ключ OpenRouter копируются с бара на сервере, токен — из `TEST_DISCORD_BOT_TOKEN`. Те же замки Hermes, что у бара. `update.sh` выбирает цель по `BARMAN_TARGET` (`prod` | `test`).
- Автовыкатка: после каждого мержа в `main` (и вручную — Actions → deploy → Run workflow). Секреты репозитория: `VPS_HOST`, `VPS_SSH_KEY` (отдельный deploy-ключ, не `companion_vps`), `VPS_KNOWN_HOSTS`. Без них выкатка пропускается с предупреждением.
- Выкатка сама выставляет замки Hermes: в `.env` `DISCORD_COMMAND_SYNC_POLICY=off`, `DISCORD_ALLOWED_ROLES=`, `DISCORD_ALLOWED_USERS` из `BARMAN_AI_USERS` (иначе `0`); в `config.yaml` — админов нет, личка выключена (см. `deploy/update.sh`). Секреты ИИ: `BARMAN_AI_USERS`, `BARMAN_AI_CHANNELS`, `BARMAN_SOUL`, `BARMAN_EMOJI`, `BARMAN_AI_MODEL` (модель разговора в OpenRouter, ставится в `model.default`; сейчас `anthropic/claude-haiku-5.5` — дешёвая; дорогие модели не ставить без нужды: каждое упоминание бармена — запрос).
- Выжимка DTF: секреты `BARMAN_DIGEST_CHANNEL` (ID канала), `BARMAN_DIGEST_USER` (имя пользователя Discord без @, бот находит его на сервере сам), `BARMAN_DIGEST_MODEL` (необязательно). Выключить, не удаляя код: секрет `BARMAN_DIGEST_CHANNEL=off` + deploy (канал в `.env` очищается, в логе «DTF digest disabled»); включить — вернуть ID канала. **Сейчас выключена.** Ключ ИИ — `OPENROUTER_API_KEY` из `.env`.
- Канал ролей: секрет `BARMAN_ROLES_CHANNEL` (ID канала). Выкатка вписывает его в `.env` на сервере — сменить канал = поменять секрет и запустить deploy. Секрета нет — `.env` не трогается.
- Команды в контейнере — только `docker exec -u 10000 barmen …` (от root появляются root-файлы и бот ломается).
- Настройки: `/root/barmen-hermes/.env` (`DISCORD_BOT_TOKEN`, `BARMAN_ROLES_CHANNEL`, `DISCORD_ALLOWED_CHANNELS`, `OPENROUTER_API_KEY`), `config.yaml` (`plugins.enabled: [barman]`, `platform_toolsets.discord: []`).
- Привязки — `/root/barmen-hermes/barman/bindings.json`. Логи — `/root/barmen-hermes/logs/{agent,errors}.log`, `docker logs barmen`.
- Один токен — один процесс: не запускать бармена ещё где-то (локально, в другом контейнере) одновременно с сервером.
